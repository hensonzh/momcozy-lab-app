## 实际授权能力与明确差异

More 原来的文字说明弹窗已移除，隐私入口进入独立 PrivacyPage。新页面按账号记录、服务所需、按需开启分组；选择具体服务后读取该服务的授权，名称来自目录，不把内部 ID 暴露为产品标题。错误的指定服务 URL 显示找不到服务，不静默改为另一个服务。

真实可修改的三项为 ibclc_case、video、ai_context，使用既有 IntakeRepository 的 /care/episodes/:id/consents。请求携带 episodeId、scope、active、expected_version、policy_version。政策版本 2026-09-08 对应后端 ConsentWrite 的 Literal，修改该契约需同时复核。两个服务所需开关独立修改，遵循后端原生 scope 规则，不复制浏览器模拟中的绑定开关。关闭必要授权会先说明后果并确认，已有历史记录不因此删除；后端关闭咨询连接的行为没有改变。

设计的 app_service 全局开关不存在原生保存契约，因此显示账号记录说明，不渲染会误导用户的开关。后端虽接受 notifications scope 的存储，但当前通知发送链路没有读取这一服务 scope；不能将其展示为实际停止提醒的开关。本页“管理通知与提醒”进入既有 /notifications/settings，用真实通知设置管理提醒。

以上两处与设计五项开关存在实质差异。因此 profile/privacy 及对应全局隐私状态保持 Need Review；不能因为新页面能打开、能保存三项而宣布五项设计全部完成。宝宝记录的数据来源与隐私导航缺口已经补齐，单独验收。

## 保存保护

开关只修改草稿，明确保存才写入。撤销操作先于新增授权发送；每个 scope 按原版本独立提交，成功响应才更新已保存状态。没有批量原子提交 API，部分成功后若失败，不显示整体保存成功；重试只继续未完成步骤，已完成的 scope 不重复写入。

网络不确定时保留原目标和版本，禁止切换草稿或服务；用户可重试相同操作，或重新读取服务器状态以消除不确定性并放弃草稿。版本冲突要求重新读取，后续编辑使用最新版本。提交过程中禁止返回及重复保存；未保存/未确认结果离开前提示。页面退出后不继续队列里的后续授权变更。
