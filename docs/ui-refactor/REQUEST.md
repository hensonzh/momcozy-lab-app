## Goal

基于当前项目中**已经梳理完成的 App UI 截图**，持续进行 UI 重构，使整套 App 的视觉设计统一到当前已经完成的 **「妈妈页」设计风格**。

设计相关上下文请优先参考以下共享会话：

https://chatgpt.com/share/6aa72c94-31e0-83ec-a7c0-af34c43b75c3

该会话包含目前妈妈页及相关模块的设计过程、设计决策、视觉方向和交互要求。开始重构前，先完整阅读并理解其中已经确认的设计思路，不要仅根据当前代码中的妈妈页自行推断设计规范。

---

## 任务边界

当前有另一个 Codex Session 正在持续梳理 App 中的页面，并将已经梳理完成的 UI 截图持续输出到项目对应目录。

因此，本任务**不负责重新梳理 App 页面，也不负责自行补齐全部页面截图**。

你的职责是：

> 持续读取当前已经梳理完成的 UI 截图，以妈妈页及上述共享会话中的设计方案为基准，通过 Figma 完成新版 UI 设计，再将确认后的设计落实到 App 中。

UI 截图目录中的内容会动态增加，因此本任务是一个**增量式 UI 重构任务**。

---

## UI 重构必须使用 Figma

对于每一个需要重构的页面，**必须调用项目可用的 Figma 插件 / Figma 能力参与 UI 设计**。

不要直接：

> 看旧截图 → 凭代码经验修改 Flutter UI。

正确流程应该是：

> 旧 UI 截图
> → 阅读妈妈页及共享会话中的设计上下文
> → 使用 Figma 进行新版页面设计
> → 检查与现有 Design System 的一致性
> → 再根据新版设计进行 App 实现。

Figma 在这里不是可选工具，而是 UI 重构流程的一部分。

对于较复杂的页面，应优先在 Figma 中完成页面布局、组件关系、视觉层级和状态设计，再进入代码实现。

## 核心设计基准

### 第一优先级：已经完成的妈妈页

以当前已经完成的 **妈妈页 UI** 作为整套 App 最主要的视觉基准。

不要机械复制妈妈页布局，而是提取其 Design System 和设计语言，并应用到其他页面。

重点包括：

* 温暖、柔和、专业的母婴产品气质
* 卡片化的信息组织
* 克制但有设计感的背景装饰
* 合理使用插画、渐变、纹理或氛围元素
* 圆角、留白、阴影和边框规范
* 清晰的字体层级
* 统一的按钮、标签、Icon 和状态组件
* 明确的模块主次关系
* 自然的页面节奏与空间层级
* 与妈妈页一致的底部导航系统
* AI + 真人专家持续陪伴的产品感

### 第二优先级：共享会话中的设计决策

其中已经确认或讨论过的内容，需要在后续页面中延续，例如：

* 妈妈页整体视觉方向
* AI 每日分析模块
* 身体与精力模块
* 今日心情模块
* 专家服务模块
* 真人专家头像的使用

* 底部 Navigation Bar
* 不同模块的默认态 / 有数据状态
* 专家服务未购买 / 已购买状态
* 页面整体视觉质感要求

遇到设计冲突时，优先遵循该会话中**后期已经确认的方案**。

## 工作对象

只处理当前项目中**已经存在于 UI 截图整理目录中的页面**。

每轮执行：

1. 检查截图目录中当前已经整理完成的 UI。
2. 判断哪些截图对应页面尚未完成新版重构。
3. 对待重构页面逐一处理。
4. 使用 Figma 设计新版 UI。
5. 将新版设计落实到 App。
6. 已经完成且符合当前 Design System 的页面不要无意义重复修改。
7. 后续截图目录出现新增页面时，再继续处理新增页面。

原则：

> 截图目录中有什么，就重构什么。

不要因为在代码中发现其他页面，就自行扩大当前任务范围。

## 每个页面的标准工作流

### Step 1：理解旧页面

读取对应 UI 截图并结合当前实现，理解：

* 页面用途
* 信息结构
* 核心功能
* 用户操作路径
* 页面状态
* 数据展示需求

不要把旧 UI 的视觉样式当作设计约束。

### Step 2：寻找已有设计模式

优先检查：

1. 妈妈页是否已经存在相同或类似模块。
2. 之前已经重构完成的页面是否存在可复用设计。
3. Figma 中是否已经存在对应组件。
4. Design System 中是否已有可复用组件。

优先复用已有模式，而不是为每个页面重新发明设计。

### Step 3：Figma 重构

调用 Figma 插件完成新版设计。

重点重新考虑：

* 页面布局
* 信息分组
* 内容层级
* 卡片结构
* CTA 层级
* 数据可视化
* 状态表达
* 留白
* 背景氛围
* 图标和插画
* 页面整体节奏

重构不是简单：

* 换颜色
* 改圆角
* 改字体
* 套妈妈页背景

而是要从页面整体体验重新设计。

### Step 4：设计一致性检查

在进入开发前检查：

* 是否明显属于妈妈页同一产品
* 是否复用了现有组件
* 是否引入了新的、不必要的视觉语言
* 是否具有足够设计感
* 是否存在组件堆叠感
* 是否保持母婴产品的温暖、专业、可信赖感

### Step 5：App 实现

再根据 Figma 设计更新 Flutter 页面。

尽量：

* 复用已有组件
* 抽象公共组件
* 使用统一 Design Tokens
* 避免页面内部 hardcode 一套独立样式

## 重构原则

### 1. UI 重构优先，不随意改业务

原则上保留：

* 功能
* 信息结构
* 数据含义
* 页面流程
* 核心交互逻辑

主要优化：

* UI
* UX
* 信息层级
* 页面布局
* 组件设计
* 状态呈现
* 页面一致性

如果旧页面存在明显 UX 问题，可以进行必要优化，但不要擅自改变核心业务逻辑。

### 2. 不能只“换皮”

重构必须达到真正的设计升级。

重点关注：

* 用户第一眼看到什么
* 核心信息是否突出
* 哪些内容应该弱化
* 模块之间是否有视觉节奏
* 页面是否有明确主次
* 是否具有品牌感
* 是否具有真实成熟 App 的设计完成度

目标不是：

> 把旧页面改成粉色圆角卡片。

目标是：

> 把整个页面重新设计成与妈妈页属于同一成熟产品体系的新版页面。

### 3. 持续沉淀 Design System

重构过程中持续抽象和复用：

* Page Scaffold
* Section Header
* AI Insight Card
* Data Card
* Status Card
* Expert Card
* Service Package Card
* Companion Plan Card
* CTA Button
* Tag / Badge
* Empty State
* Bottom Sheet
* Dialog
* Navigation Bar
* Loading / Error State

后续新增页面优先复用这些组件。

## 页面状态

如果截图中体现了不同状态，或者当前页面本身存在明确状态变化，需要一并设计。

例如：

* 默认状态
* 无数据状态
* 有数据状态
* Loading
* Error
* Disabled
* 未购买服务
* 已购买服务
* 服务进行中
* 服务已完成

特别是服务类模块：

未购买状态可以承担服务发现和转化；

购买后应切换为服务中的体验，例如展示：

* 我的陪伴计划
* 当前服务阶段
* IBCLC 专家
* 服务进度
* 下一步行动
* AI 与专家的持续陪伴信息

不要让购买前和购买后仍然表现成同一个营销入口。

---

## 动态新增 UI 截图

因为另一个 Codex Session 会持续补充 UI 截图：

* 不要假设当前截图目录已经完整。
* 当前处理完成 ≠ 整个 App 永久完成。
* 每次继续执行任务时先检查是否出现新截图。
* 新增截图只处理新增或尚未重构的页面。
* 不要重新扫描并重构已经稳定完成的页面。
* 新页面必须继续沿用已经形成的 Design System。

随着页面不断增加，Design System 应越来越稳定，而不是越来越分散。

---

## 页面验收标准

每个页面完成后检查：

* 是否与妈妈页属于明显同一设计体系
* 是否符合共享会话中的设计方向
* 是否经过 Figma 设计，而非直接代码改样式
* 是否具有成熟产品的视觉完成度
* 信息层级是否清晰
* 页面是否有足够设计感
* 卡片、按钮、标签和 Icon 是否统一
* 留白与间距是否合理
* 是否避免组件堆叠
* 是否复用了公共组件
* 长页面是否完整适配
* 是否存在 Overflow / clipping / layout error
* 原有业务流程是否正常
* 不同页面之间是否存在视觉断层

## 最终目标

建立以下持续协作流程：

**Codex Session A**

> 持续梳理 App 页面
> → 输出完整 UI 截图

**当前 Codex Session**

> 读取已经整理好的 UI 截图
> → 参考妈妈页与共享设计会话
> → 调用 Figma 完成新版 UI
> → 复用 / 完善 Design System
> → 更新 Flutter App 实现

最终随着截图不断补充，逐步完成整套 App 的统一视觉重构。

如果旧 UI 与当前新版设计发生冲突：

> **以妈妈页、共享会话中的最新设计决策，以及已经稳定完成的新版 Figma 页面为准。**
